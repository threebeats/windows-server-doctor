Three backups on my laptop were lying about their age

One of them was off by 64 days. Another cost me a night of work, because I trusted the date in its filename instead of the date on the file.

By Elias Easton  ·  2026  ·  90 seconds or your money back

The one that cost me a night

Halloween night, my service wouldn't start. I made a backup before touching anything — tidy, dated, exactly what you're supposed to do.

It didn't fix anything. So I went to the obvious fallback: the previous config. The good one. The one that worked.

openclaw.json.bak-desire-20261031-164439

October 31st. Four days old. Reasonable.

Except its actual modification time was October 12th.

Three in one folder. I found the third one only because I'd written a checker for the first two.

Why this happens, in one line

Copy-Item preserves the source file's modification time. The name gets today's date. The body keeps last month's timestamp. And the name is the part that looks authoritative.

That's the whole bug. The tool copies the file perfectly — bytes intact, hash identical. It just carries the old timestamp along with it, like luggage you didn't pack.

Nothing errors. Nothing warns. You get a backup that is technically a faithful copy and practically a document that lies about when the world looked like this.

The fix is one line

Copy-Item $Path $dest -Force
(Get-Item $dest).LastWriteTime = $now   # <-- the whole fix

Write the name, then force the file's own timestamp to agree with it. Now the name and the body are the same fact, and neither can drift.

If you'd rather not have a date to be wrong about at all, use the content hash instead. A file named by the SHA256 of its bytes can't lie — if the name is right, the contents are right, by construction.

But it's bigger than backups

Once I'd found it, I started recognising the shape everywhere. It's not "a bug in Copy-Item". It's a whole family:

  1. A config that parses but is invalid. Braces balance, so the file "loads" — and then the loader rejects a field and refuses to start. Went around that loop all night: the JSON was fine, which is not the same as the config being fine.
  2. A process that reports "online" and returns 401. The supervisor said healthy. The logs said it had been unauthorised for four days. Nobody was watching, because the status column was green.
  3. A state file that round-trips and matches nothing. Written correctly, read back, parsed without error — and every comparison silently failed. The filter could never be true. It looked like it was working, forever.
  4. A filename with a date you typed yourself. The one that started this.

A system that reports status without checking reality is worse than no status at all — because you stop looking.

The six checks I now run

I wrote these as a script anyone can run on Windows. No install, no admin, no network, no telemetry. Six checks, one verdict, and an exit code you can wire into anything:

#CheckCatches
1Config parses and survives the shapes loaders rejectthe crash-loop class
2Backup filenames vs real modification timesthe lying-backup class
3Logs scanned for auth errors in a time windowthe "online but dead" class
4State files written, read back, comparedthe eaten-state class
5Scheduled tasks that have never actually runthe scheduled-but-forgotten class
6Disk headroom and runtime versionthe boring ones that bite
 
.\doctor.ps1 -ConfigPath .\config.json -StateFiles .\state.json
# exit 0 = clean   1 = warnings   2 = will not self-heal

It found the 19-day liar on a real machine. It also found the 64-day one, on a second run, after I'd already "fixed" the folder.

The six rules

  1. Parse ≠ validate. Balanced brackets say nothing about whether the fields are real.
  2. Never trust a date you typed into a filename. Read the mtime.
  3. "Online" is not "working." Check what it's actually doing, not what the column says.
  4. Round-trip your state. Write it, read it, compare it — in a test, not in production.
  5. A filter that can never be true hides everything. Prove the condition can succeed before trusting silence.
  6. Write the record before you report. If the write fails, stay quiet — a missed alert is recoverable, a wrong one teaches people to ignore you.
